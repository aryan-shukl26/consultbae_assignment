# Data Issues Report

A record of every data quality problem found across the 3 source files, and how each was handled. This report is meant to be included directly in the README, or referenced from it.

---

## Missing value handling

`dropna()` was applied only to `source2_gig_workers.csv`, where it removed the single fully-blank planted row (32 → 31 rows). It was **not** applied to source1 or source3, since a direct null-count check on the raw data confirmed neither file had any missing values at the cell level — applying a blanket drop there would have been an unnecessary blunt instrument with no upside. This was verified directly (checking `.isna().sum()` per column on each raw file) rather than assumed.

For all three files, individual field-level normalization functions (`normalize_phone`, `normalize_email`, etc.) independently return `None` for any value that's missing or fails to parse, rather than relying on row-level dropping — so a row with one bad field doesn't silently disappear entirely; only the specific unparseable field is flagged as null.

## source1_naukri_applicants.csv

### 1. Inconsistent phone number formats
Phone numbers appeared in at least 5 different formats: plain 10-digit (`9000000254`), with country code (`+919000000254`, `919000000231`), with a leading zero (`09000000287`), and with a hyphenated country code (`+91-9000000131`).
**Resolution:** `normalize_phone()` strips all non-digit characters, removes the `91` country code prefix and any leading `0`, and reduces every number to a bare 10-digit string. Any value that doesn't reduce to exactly 10 digits is set to `None` rather than guessed, to avoid silently storing malformed data.

### 2. Inconsistent city names
City values had inconsistent casing and spacing (`GURGAON`, `Gurgaon`, `gurugram ` with a trailing space) and used different names for the same place (`Gurugram` vs `Gurgaon`; `Delhi NCR` / `New Delhi` / `Delhi`).
**Resolution:** `normalize_city()` lowercases and trims whitespace, then maps known synonyms to a single canonical value (`gurugram → gurgaon`, `new delhi` / `delhi ncr` → `delhi`).

### 3. Inconsistent email casing
Some emails were fully uppercase (`ISHA.CHOPRA95@MAILTEST.EXAMPLE.ORG`) while most were lowercase — this would break exact-match comparisons during cross-file merging.
**Resolution:** `normalize_email()` lowercases and trims every email before it's used for matching or storage.

### 4. Inconsistent Applied Date formats
The Applied Date column mixed at least 4 formats: `DD-MM-YYYY` (`24-07-2026`), `YYYY-MM-DD` (`2026-08-08`), `D Mon YYYY` (`7 Jul 2026`), and `MM/DD/YYYY` (`07/13/2026` — the `/13/` confirms this can't be `DD/MM`, since there's no 13th month).
**Resolution:** `normalize_applied_date()` tries each known format explicitly, then falls back to pandas' flexible date parser (`dayfirst=True`) for anything unmatched. **Known limitation:** a small number of genuinely ambiguous dates (e.g. `01/02/2026`, which could mean Jan 2 or Feb 1) cannot be resolved with certainty from the data alone; the fallback makes a best-effort guess rather than leaving these blank, which is a deliberate trade-off favoring completeness over certainty.

### 5. Inconsistent CTC units
The Current CTC column mixed raw rupee figures (`417964`) with values apparently expressed in lakhs (`4.2`, `8.3`, `11.2`), with no unit column to disambiguate.
**Resolution:** `normalize_ctc()` applies a heuristic — any value under 1000 is treated as lakhs and converted to rupees (×100,000); values ≥1000 are assumed to already be in rupees. All CTC values are stored in one consistent unit (rupees). This is a judgment call based on realistic salary ranges, not a certainty, and is documented as such rather than presented as verified fact.

### 6. Exact duplicate record (R. Verma / Rohit Verma)
The same person appeared twice — once as an abbreviated name (`R. Verma`) and once in full (`Rohit Verma`) — with identical email and phone number.
**Resolution:** Detected via `duplicated(subset=['norm_email', 'norm_phone'])`. Rows were sorted so the longer name came first, then `drop_duplicates(keep='first')` retained the fuller name and dropped the abbreviated duplicate. Confirmed: 42 → 41 rows.

### 7. Same person, alternate email on file (Nikhil Chopra)
One person appeared twice with the same phone number and city, but two different email addresses (`nikhil.chopra70@...` and `alt.nikhil.chopra70@...`).
**Resolution:** Both rows were retained (not dropped, since each carries a genuinely different email) and grouped under a shared `dedup_group_id`, generated by grouping all rows on `norm_phone` and assigning every row in a multi-row phone group the same id. This lets the pair resolve to one person downstream while preserving both emails in the audit trail, rather than one being silently discarded — unlike case #6, which was a true duplicate with no new information in the second row.

### 8. Inconsistent skill casing
Skills were written with inconsistent capitalization (`"LangChain"`, `"REST APIs"`, `"MongoDB"`), which would prevent exact matching against the same skills listed in lowercase in source2.
**Resolution:** All skill values normalized to lowercase (`', '.join(x.strip().lower() for x in skills.split(','))`) for consistent cross-file comparison.

**Final source1 output:** 42 raw rows → 41 rows in `df1_final` (1 exact duplicate removed; the Nikhil Chopra pair intentionally kept as 2 rows sharing one `dedup_group_id`, not collapsed to 1).

## source2_gig_workers.csv

### 1. Blank row
One row was entirely empty across every column.
**Resolution:** Removed via `dropna()`, applied specifically to this file since it's the only one of the three with a genuinely blank row in the raw data. Confirmed: 32 → 31 rows.

### 2. Shifted-column malformed row
One row's values were shifted across the wrong columns entirely — e.g. a skills list (`"react, javascript, mysql"`) appeared in the position where an email should be, and an email appeared where a name should be. This row was also a near-duplicate of an already-correctly-formatted Isha Chopra row elsewhere in the file. Because every field in this row was still *populated* (just in the wrong place), `dropna()` did not catch it — a separate, targeted check was needed.
**Resolution:** Filtered using `df2_final['norm_email'].str.contains('@', na=False)` — since the shifted row's "email" field held a skills list with no `@`, this correctly isolates and removes it while leaving valid emails untouched. Confirmed: 31 → 30 rows. A correctly-formatted version of the same person's data already existed elsewhere in the file, so no information was lost.

### 3. Inconsistent rate formats and units
The `rate` column mixed hourly rates (`"1415/hr"`) and monthly rates (`"73k/month"`) with no common unit, and no standard hours-per-month figure exists to convert one into the other without introducing an unverifiable assumption.
**Resolution:** Rather than force a lossy unit conversion, `normalize_rate()` splits each value into two columns: `rate_value` (numeric) and `rate_type` (`hourly` or `monthly`). Result: 16 hourly / 14 monthly, 0 unparsed. This preserves the original data faithfully and leaves unit conversion as an explicit downstream decision rather than baking in an assumption.

### 4. Status has 3 states, not a clean binary
The `status` column contains `active` (21), `inactive` (6), and `paused` (3). `paused` doesn't cleanly fold into either of the other two without losing information.
**Resolution:** Kept as a 3-state field via `normalize_status()` rather than collapsed into a binary, to avoid silently discarding a meaningful distinction the source data intentionally captured.

### 5. Inconsistent email casing
Same issue as source1 — some emails used mixed/uppercase.
**Resolution:** Same fix — lowercased and trimmed via `normalize_email()`.

**Final source2 output:** 32 raw rows → 30 rows in `df2_final` (1 blank row + 1 malformed row removed).

## source3_cbnexus_contacts.csv

### 1. Embedded duplicate header row
A second copy of the CSV header row (`Name, Phone Number, City, Verified, Projects Completed`) was embedded partway through the file as if it were a data row, parsing into a fake "person" named `Name` with no valid data. Every field in this row was populated (with the literal header text), so it would not have been caught by `dropna()` even if applied to this file.
**Resolution:** Located at a fixed position (`df3.iloc[14]`, confirmed by inspection before dropping) and removed via `df3.drop(index=14).reset_index(drop=True)`. Verified after the drop that `(df3['Name'] == 'Name').sum() == 0` and that row counts around that index still contained real people, confirming no genuine record was accidentally dropped in its place. **Note on approach:** dropping by fixed index position works but is fragile if cell execution order changes upstream row indices; a value-based filter (`df3[df3['Name'] != 'Name']`) would be more robust for reuse, though both were verified to produce the same correct result here.

### 2. Inconsistent `Verified` boolean representation
The `Verified` column used four different representations of the same boolean: `Y`, `N`, `yes`, `No`, `Yes`.
**Resolution:** `normalize_verified()` collapses all variants to a proper boolean (`True` for `y`/`yes`, `False` otherwise).

### 3. Two people sharing the same name and city (Arjun Mehta)
Two records both read "Arjun Mehta," both in Noida, but with different phone numbers (`9000000131` vs `9000000272`), different verification status, and different project counts (9 vs 14).
**Investigation:** Cross-referenced both phone numbers against source1 and source2. One phone number matches a Naukri job applicant record in source1 (with a corresponding email `arjun.mehta9@...`); the other matches a separate gig-worker/CBNexus-only identity with a different email (`arjun.mehta77@...`) and no matching Naukri application. This confirms two distinct people who happen to share a common name — not a data entry duplicate.
**Resolution:** Kept as two separate person records rather than merged. This is a deliberate decision to avoid a false merge that would silently combine two different people's project history and verification status under one identity — arguably a more serious error than under-merging, since it would corrupt the account of both people rather than just leaving two records slightly less linked than they could be.

### 4. `Projects Completed = 0` for one contact (Sahil Malhotra)
One record shows 0 completed projects, while the rest of the file's values range from 1–15.
**Investigation:** No `NaN`/missing values exist anywhere in this column (confirmed across all 30 rows), so this isn't a parsing artifact — it's a genuine `0` in the source data.
**Resolution:** Kept as-is. Plausibly a legitimate new/unverified contact with no completed projects yet; flagged here for visibility rather than silently treated as either "real" or "missing," since the data alone can't disambiguate which it is.
